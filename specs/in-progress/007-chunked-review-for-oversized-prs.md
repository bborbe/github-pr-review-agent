## Summary

- The watcher's size gate parks an oversized PR at `human_review` instead of reviewing it: measured over 17 days, 112 of 1,424 review requests (7.9%, 75 unique PRs) were parked, and 77 resolved parks were merged with the bot review never run.
- The agent cannot absorb those PRs today: the execution phase runs one review pass over the whole diff, and a diff above the park ceiling overflows the model's context window — the park exists because the reviewer cannot do it in one pass.
- This change makes the agent review a large diff in bounded chunks: the changed files are partitioned (path-sorted, ~300 added lines and ~15 files per chunk, a file never split from its `_test.go` sibling), each chunk gets one review run, and the chunk verdicts merge worst-wins into exactly one posted review.
- Chunking engages only above ~500 reviewable added lines; below that the review path is unchanged (one run, one unscoped prompt, one verdict).
- Every chunk is observable in the pod log (`review chunk <i>/<n> files=<F> additions=<A>`), so the deployed behavior is verifiable without reading the review body.

## Problem

The watcher's size gate parks any PR whose reviewable diff exceeds `MAX_ADDITIONS` (1200 added lines, dev and prod, verified 2026-09-11) at `human_review` instead of spawning a review pod. Measured over 17 days: 112 parks out of 1,424 review requests (7.9%), 75 unique PRs; 77 of the resolved parks were merged with the bot review never run — a park is, in practice, an unreviewed merge, and the review gate branch protection is supposed to enforce was bypassed each time. The agent cannot absorb these PRs: the execution phase runs a single review pass over the whole diff, and a diff above the park ceiling overflows the model context window — that is exactly why the park exists. Nothing in the agent can review a PR in pieces today, so the park is the first answer to any large PR rather than a last-resort guard.

## Goal

After this work the agent can review a large diff in bounded chunks and post one merged verdict: a big-but-reviewable PR gets the reviewer's full attention per chunk instead of one pass over the whole diff. A PR above the chunking threshold has its changed files partitioned into bounded chunks; each chunk runs one review scoped to its files; the merged review carries one section per chunk and exactly one verdict — the worst of the chunk verdicts — and an incomplete chunk can never yield an approve. Below the threshold the review path is unchanged. The per-PR soft budget stays the outer cap with today's expiry semantics (salvage, `human_review`, never a partial verdict). The watcher is untouched: the park ceiling keeps its current value, and relaxing it becomes a values-only decision because the agent can now review what previously had to be parked.

## Non-goals

- Do NOT change the watcher — no code change and no threshold value change (`MAX_ADDITIONS` stays 1200, `MAX_CHANGED_FILES` stays 100). Raising the park ceiling is a separate operator decision once chunked reviews are proven in prod.
- Do NOT change the model, the review depth (`REVIEW_MODE`), or the per-chunk review depth — each chunk gets the same review instructions a single run gets today.
- Do NOT change the `ai_review` phase or its host-side whole-diff inlining.
- Do NOT add an extra synthesis LLM pass — the merge is deterministic Go.
- Do NOT split a single file across chunks.
- Do NOT run chunks in parallel.
- Do NOT add an opt-out or disable knob for chunking — invariant; if a future consumer demands one, that is a separate spec.
- Do NOT re-implement `.reviewignore` in the agent — the watcher's exclusion logic stays watcher-side.

## Desired Behavior

1. **Changed-file inventory.** The mechanical funnel's result carries, alongside its existing fields, the PR's changed-file list with each file's added-line count, computed against the same resolved base the changed-file scan already uses (`git diff --numstat` over that base; binary entries count 0). The existing funnel contract — ran / findings JSON / fail-detail semantics — is unchanged; the inventory is additive. When the added-line counts cannot be computed, chunking is skipped and the review proceeds as a single unscoped run with a glog warning naming the failure; no `review chunk` line is emitted on this path — the warning is the detection signal.
2. **Engagement and thresholds.** Chunking engages when the total added lines across the changed-file set is strictly greater than `REVIEW_CHUNK_ENGAGE_ADDITIONS` (default 500). At or below it, the review runs exactly as today: one run, one unscoped prompt, one verdict. Two further knobs bound each chunk: `REVIEW_CHUNK_MAX_ADDITIONS` (default 300) and `REVIEW_CHUNK_MAX_FILES` (default 15). All three are read from the environment, validated at startup (each must be ≥ 1; an invalid value fails startup naming the variable), and none of them can disable chunking.
3. **Partition.** Path-sorted greedy partition: files are taken in sorted path order and appended to the current chunk until adding the next unit would exceed either bound; the chunk then closes and a new one starts. A unit is a changed file together with its non-test sibling (`X.go` and `X_test.go` in the same directory) when both are changed — the pair is never separated. A chunk always accepts its first unit even when that unit alone exceeds the additions bound; a file is never split. The chunks cover the changed-file set exactly once each, and the partition is deterministic for a given input.
4. **Per-chunk execution.** One sequential claude run per chunk, each with a prompt scoped to its chunk: the prompt names the chunk's files, instructs the review to cover only those files, and carries the funnel findings for those files only — same basename matching as the diff-anchor filter, count recomputed, so each chunk's prompt stays bounded by its own files; a chunk with no findings still reports the funnel as having run. The clone, the allowlist check, and the mechanical funnel run once per review, not per chunk. Each chunk run emits exactly one glog line `review chunk <i>/<n> files=<F> additions=<A>` (i 1-based, F = files in the chunk, A = the chunk's added lines) before that chunk's run starts, so n lines appear before any verdict exists; a below-threshold run emits one line with n = 1.
5. **Merge.** The chunk outputs are merged in Go with no extra model call: each chunk contributes a section labelled `Chunk <i>/<n>`, per-chunk verdict blocks are removed, and the merged body ends in exactly one verdict block. The merged verdict is worst-wins over the chunk verdicts — `request-changes` if any chunk parsed to `request-changes`, `approve` only if every chunk parsed to `approve`. The existing Go-side blocking gate (`ApplyBlockingGate`) is applied to each chunk's verdict before the fold, so a chunk that emits `approve` while its verdict block carries a `blocking: true` comment (or a critical/major severity) contributes `request-changes`; without this, the merge's synthesized comment-free verdict block would silently disable the blocking gate on the chunked path. The synthesized block also carries the union of the per-chunk `concerns_addressed` entries (worst disposition wins: any `not-verified` stays `not-verified`), so the downstream unverified-concerns gate stays live on the chunked path. A chunk whose output carries no parseable verdict contributes `request-changes` (the existing fail-closed parser). The merged body is what is written to `## Review` and what the unchanged posting path posts — one review, one event.
6. **Budget and failure routing.** The per-PR soft budget remains the outer cap and starts when the first chunk run starts. Each chunk runs under the earlier of the outer deadline and `now + max(remaining time ÷ remaining chunks, 60s)`. A run cut off by either deadline is an expiry: the cut-off chunk's streamed partial is salvaged under `## Salvage` with the chunk named, the loop stops, no `## Review` is written, and the existing budget-expiry result routes the task to `human_review` (done status, unchanged message). A chunk run error that is not a deadline expiry keeps today's path: the step returns failed and the controller retries; no partial review and no salvage is written. The elapsed time handed to the concerns gate is the sum of the chunk runs' elapsed time.

## Constraints

- The mechanical funnel contract is unchanged: `Ran` / `FindingsJSON` / `FailDetail` semantics and the findings JSON shape stay as they are; the changed-file inventory is additive.
- Below the engage threshold the execution path is unchanged: one runner invocation, the same unscoped prompt content, one verdict, one posted review.
- The verdict set stays binary (`approve`, `request-changes`). No `comment` verdict value is introduced anywhere; a chunk that emits anything else fails closed to `request-changes` through the existing parser.
- The posting path, the verdict gates (funnel-ran, concerns-not-verified, blocking), the `## Review`-present shortcut, the salvage heading and marker, the allowlist, and the clone path are unchanged.
- The `ai_review` phase is unchanged and chunk-agnostic: it consumes the merged `## Review` as it consumes today's single review; its host-side whole-diff inlining is untouched.
- Chunks run sequentially in one container; peak resource use equals a single run's.
- The merged `## Review` contains exactly one verdict block (the merged verdict); per-chunk verdict blocks are removed before the body is written.
- The per-PR soft budget (default 25m, floor 60s) is unchanged and is never exceeded; the per-chunk share never extends past the outer deadline.
- Chunk boundaries come from the changed-file inventory only: a file is never split across chunks, and a file plus its `_test.go` sibling always share a chunk.
- Reviewable additions = added lines from the worktree diff (numstat) over the funnel's changed-file set against the funnel's resolved base; binary entries count 0. The agent does not re-implement the watcher's `.reviewignore` subtraction — a path excluded by the watcher but present in the worktree diff still counts, which only makes chunking engage earlier, never later.
- The chunk log line is emitted with the exact format `review chunk <i>/<n> files=<F> additions=<A>` at glog `V(2)` (pod logs carry `V(2)` lines — verified live on a prod review pod 2026-09-11).
- The three thresholds are read from the environment with the fixed names and defaults above; each must be ≥ 1; none disables chunking.
- DoD rules apply: errors via `github.com/bborbe/errors` (no `fmt.Errorf`), no debug output, `context.Context` threaded through IO, doc comments on exported symbols, `make precommit` clean, no `exclude` / `replace` in `go.mod`.
- CHANGELOG: `## Unreleased` is created below the preamble and above the newest `## vX.Y.Z` section (currently `## v0.10.1`) — never between the title and the preamble.

## Failure Modes

| Trigger | Expected behavior | Detection | Recovery |
|---|---|---|---|
| A chunk's claude run errors (not a deadline expiry) | The step returns failed; no `## Review` and no `## Salvage` written; the controller retries the phase (today's semantics) | Pod log `execution claude run failed`; failed status published to Kafka | Automatic controller retry re-runs the phase from scratch; no manual action |
| A chunk run is cut off by its deadline (share or outer budget) | Salvage the cut-off chunk's partial under `## Salvage` naming the chunk, stop the loop, done + `human_review` with the unchanged budget message; no verdict posted | Pod log budget-expiry line naming the chunk; task phase `human_review`; `## Salvage` present | Human reviews the salvage; a re-trigger re-runs the whole review (no `## Review` exists, so the shortcut does not fire) |
| A chunk's output has no parseable verdict | That chunk contributes `request-changes`; the merged review posts `request-changes` with the fail-closed reason logged | Pod log `pr-reviewer fail-closed to request-changes` | Re-trigger; a human decides — never merged unreviewed |
| A chunk emits `approve` while its verdict block carries a `blocking: true` (or critical/major) comment | That chunk contributes `request-changes` (`ApplyBlockingGate` applied per chunk before the worst-wins fold); the merged review posts `request-changes` | Merged verdict `request-changes`; pod-log fail-closed line | Re-trigger; a human decides — never merged unreviewed |
| Added-line counts cannot be computed | Chunking is skipped; the review proceeds as today's single unscoped run; a warning names the failure | glog warning naming the diff computation failure | None needed (today's behavior); if it recurs, fix the diff computation |
| A single file (or sibling pair) exceeds the per-chunk additions bound | It forms its own chunk and is reviewed alone; if that run still overflows the model context it lands in the run-error row | Chunk line shows additions greater than the bound | None automatic — a file is never split; the run's own failure routing applies |
| A chunk consumes more than its reserved share while budget remains | The run is cut off and routed to `human_review` (expiry semantics); the completed chunks' work is not posted | Pod log budget-expiry line naming the chunk index | Operator tunes `REVIEW_CHUNK_*` or `REVIEW_MAX_DURATION`; re-trigger |
| GitHub API rate limiting during the final post | Unchanged: chunking multiplies claude runs, not API calls — the review posts once per review | Existing posting diagnostics block in the task file | Existing poster retry and backoff, unchanged |
| Two reviews race on the same PR (re-trigger) | Unchanged from today: the `## Review`-present shortcut advances to `ai_review`; same-SHA reviews stack, newest wins | Existing diagnostics block | None needed |

## Security / Abuse Cases

- What an attacker controls: the PR's file names (through the changed-file list) and the diff content. The per-chunk prompt embeds the chunk's file list — PR-author-controlled text inside the prompt. It is neutralized exactly like funnel finding text (code-fence neutralization) and emitted as data (a list), never interpreted as instructions.
- Trust boundaries are unchanged: the allowlist check and the clone happen once, before chunking, on the same inputs as today; chunking adds no network surface and no new write — the review still posts exactly once.
- What can hang or retry forever: each chunk run is bounded by its deadline and the loop is bounded by the per-PR budget; there is no in-process retry loop — a failed chunk exits to the controller's existing retry path, which is capped as today.
- What must be validated: the three `REVIEW_CHUNK_*` values (≥ 1 at startup, fail fast); file names are never passed to a shell — the partition and the log line are pure string work, and no command is constructed from a file name.
- No new data exposure: the salvage path writes model output into the task file exactly as today; no secret or credential is added to the prompt, the log line, or the review body.

## Do-Nothing Option

The current approach is not acceptable.
